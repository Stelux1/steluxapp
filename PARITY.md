## Deliberate pilot-boundary crossings

Inside a pilot the other pilot's records are refused (hosted profile). These places cross that boundary on purpose:

1. **Isometric summary** (`isoSummariesFor`, `server/iso-summary.ts`): aggregates per visible isometric (progress, quality, blocker counts, list flags, KPI facts, Material status %, MTO budgets, punch counts, hydrotest state, QA counts for the Iso overview badges), delivered in both pilots. One label is carried: `testSystemName`, only for a test system of the isometric's own project or of none.
2. **Copy isometrics / Add new** (`copyParts`, `server/release-access.ts`): welds, materials and calculations are each judged with the account's profile in the pilot that owns them and, since wave 3, with the profile of the main project copied into (sec1-005). A copy never carries completion fields, X Ray % or punch progress (sec1-006).
3. **Import all project data** (wave 4, `w4-project-import`): one file writes welds (owned by Weld Pilot) and material lines (owned by MTO Pilot); each part is judged by the account's profile in the pilot that owns it, for the open main project. The second security review covers it.

Read-only borrowings: an account limited to one main project receives the code and name of the welders its readable welds name (`welderStamps`, `925062a`), never the welder records. The ISO Book offers parts the account may print in its other pilot, worked out per isometric, only when the project is on in that pilot and the account reaches its main project there (scn-SB-N8, sec1-003). The ITP register is readable in MTO Pilot for any account that can read isometrics (area 64); linking needs Edit on the isometric (W3, `w3-iso-page-dialogs`).

## Local behavior tested, source mutation behavior still unverified

These rules are implemented explicitly and covered by local tests. They must not be described as proven source rules merely because they are reasonable. They come from the first version and were not re-run by hand in this audit (the automated tests still pass):

- Atomic rollbacks across a multi-line receipt, stock, counters and audit history; stock never goes negative; optimistic record versions.
- Prevention of duplicate delivery lines, excessive returns, invalid dates / quantities, stale edits and mismatched spool / isometric links.

## Remaining differences and why

Ordered by how much the user will notice them. "Client" and "owner" refer to `CLIENT-QUESTIONS.md`.
